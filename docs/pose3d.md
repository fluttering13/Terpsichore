# A+B 3D Pose

首次 checkout 後請執行 `git lfs pull` 取得 NLF ONNX 權重；CI checkout 已啟用 LFS。沒有私人 A/B 測試影片時，兩項依賴影片的 Android 儀器測試會標記略過，JVM 幾何與資源預算測試仍可執行。

Android 本機推論。A+B → AI 設定 → 3D Pose 設定可調整推論 FPS 與內插。預設為 **NLF-L INT8、10 FPS、開啟內插**。MediaPipe Heavy 已移除，舊 Heavy 設定會遷移到 NLF、10 FPS。

3D Pose 按鈕會擷取當下 A/B 裁切與倍速的快照。共同時間長度取兩者調整後長度的較短者；輸出時間 `t` 對應各來源的 `trim.start + t * rate`。分析期間不會再做一次 AI 對齊。

結果頁提供原影片／3D 骨架切換、播放與拖曳時間軸，以及單指軌跡球旋轉／雙指縮放。旋轉以單位四元數累積並正規化，可跨過正上方與正下方，不再限制俯仰角；靠近視窗邊緣拖曳可滾轉。雙指縮放不旋轉，切換手指数時重設拖曳起點以避免視角跳動。重設視角恢復預設朝向與縮放；匯出使用同一份不可變視角快照。A/B 固定並排，已移除疊合按鈕與繪製。骨架以骨盆為中心、保留來源相機方向，沒有額外自動修正兩支影片的朝向。

推論工作由 app 管理，返回上一頁不會取消；可從 A+B 的 3D Pose 按鈕再次查看進度。只有按「取消分析」才停止，正在執行的原生影格會先完成再釋放模型。這支援 app 內頁面切換，尚非可跨 Android 終止程序持續運作的前景服務。

已儲存的 A+B 專案各自保留一組成功 3D 結果，位於 app 文件目錄 `saved_projects/pose3d/<base64url-project-id>.json`，包含 A/B 原始骨架採樣、完成時的模型／FPS／內插設定及對應的影片／時間軸。開啟已儲存專案的 3D 頁面時先保存目前專案快照，推論完成後自動寫入該專案；推論後才第一次存專案，也會攜帶結果並對應到搬移後的永久影片路徑。推論中存專案則在完成時寫入。多個專案不共用同一份結果，重啟及分析別的影片後仍可還原。

尚未儲存的比較另保留最近一組 `pose3d-last.json`；開啟／儲存舊專案時會將符合的舊快取遷移到專案。還原會檢查影片路徑、長度、裁切與倍速，避免誤用不符目前時間軸的骨架。結果頁設定只影響下一次推論；重新推論成功才替換結果，取消或失敗保留原本的專案結果。來源影片仍須存在。

儲存按鈕將目前視角與排列輸出為 720×720、30 FPS、無音軌的 MP4，存到 A+B 原本設定的相簿。開啟 post-processing 時，先補最多連續 2 個漏偵測採樣點，且前後有效採樣須相距不超過 0.6 秒（調整後的共同時間軸），再內插播放／輸出影格。長時間缺失及缺少前／後有效姿勢的首尾區段不補。原始偵測結果與快取不會改寫，既有結果也適用。停用內插則維持原始前一採樣姿勢，包含原本的空白。取消匯出會清除未完成的暫存輸出。

3D 頁面、設定、進度與自訂錯誤提示跟隨 App 的中／英文選擇。分析百分比下方顯示預估剩餘時間：模型載入時顯示「估算中」，開始採樣後依 A/B 合計完成比例與實際牆鐘耗時估算，每次採樣完成更新。返回再進入沿用同一工作計時，重新推論會重置，取消後不再顯示預估；100% 整理／快取階段顯示「正在整理結果」。預估不包含尚未完成的收尾時間，溫度及資源競爭可能使估算變動。

手機的 `test` A+B 專案快取：5 FPS、A 29 個採樣中僅共同時間 2.8 秒漏偵測，2.6 與 3.0 秒有效，B 無缺失。新邏輯補回此處，在 30 FPS 回放檢查 A 的 164 個輸出時刻皆有有效骨架，停用 post-processing 時仍保留原始缺失。此為短暫缺失的線性估計，不等同重新估測該影格的真實姿勢。

## 立體骨架顯示

骨架改用膠囊肢體、球形關節及簡化胸部／骨盆。`shaders/pose_3d.frag` 使用正交射線求交，逐像素選最近的表面，再計算光照與深度明暗；不再以整根骨頭的平均深度決定遮擋。A/B 各有固定畫面區域，骨盆置中後才旋轉，側面也不會重疊。兩者沿用相同縮放比例與四元數視角，可用正面／側面／俯瞰按鈕切換。

畫面與 MP4 匯出共用同一渲染器。Shader 載入失敗時畫面提示並暫用簡化骨架；匯出必須成功載入立體渲染器。保留正交投影以方便比較，不加入遠近透視縮放。模型僅有腳踝點，未新增無資料支持的腳掌朝向；地面格線是方向參考，不代表估計出的實際地面或接觸位置。

## 模型

| 選項 | Android 執行路徑 | 權重大小 |
|---|---|---:|
| NLF-L INT8 | ONNX Runtime CPU、QDQ INT8 backbone、H36M-17 canonical heads、5 次增強推論融合 | 126,298,385 bytes |

權重位於 `android/app/src/main/assets/pose3d/`，SHA-256 記錄在該目錄的 `manifest.json`。NLF 隨 APK 打包，第一次使用另解包到 app 的 no-backup 目錄，因此另需約 126 MB 儲存空間。Heavy 的權重及 tasks-vision 依賴均已從 app 移除。

開始前讀取 CPU 核心及最高頻率、總／可用 RAM、Java heap 上限與溫度狀態。每個工作預留估計 640 MiB，另保留至少 1 GiB（或系統低記憶體門檻的兩倍）。需至少 6 核、4 個較快核心、6 GiB RAM、384 MiB heap，且可用記憶體足夠且未達中度過熱，才使用兩路 A/B 並行；其餘依序處理。每路各自持有模型與追蹤器，每支影片仍依時間順序推論。這是同一程序內的工作執行緒，並非額外 Android 程序。

ORT 每路分配 1–4 個 CPU 執行緒，關閉閒置忙等。第二個模型載入前再次檢查資源，不足時退回依序處理；每影格之間檢查記憶體與溫度，必要時限制為一個活躍推論。已載入的模型於工作結束或取消後釋放。

NLF 的 ML Kit Accurate 僅負責取得 2D 人體框；3D 座標由 NLF 產生。此框偵測使用 SINGLE_IMAGE_MODE，避免 A/B 交錯處理時受時間追蹤狀態影響；原本 A+B 的 2D AI 對齊流程不受影響。原始相機假設為 55° 視角，包含線性 RGB 影像金字塔、5 個旋轉／尺度／亮度／鏡像裁切、完整透視還原、尺度一致化與不確定度加權幾何中位數融合。INT8 量化與 2D 框偵測器不同，結果不保證與先前 Python 桌面版逐點相同。

## 重建與驗證

- `tools/prepare_pose3d_android.py`：以既有校準 ONNX 與 canonical query weights 準備 Android 權重；檢查正常頭輸出不變及鏡像頭與原始 TorchScript decoder 一致。
- `tools/pose3d_geometry_fixtures.py`：從原始模型產生 JVM 測試資料，驗證真實 A/B 預測的透視還原及含鏡像／邊界的裁切。
- `test/core/pose_3d_test.dart`：時間軸、倍速、內插與設定遷移。
- `NlfGeometryTest`：與原始 TorchScript 數值比對。
- `Pose3dDeviceTest`：實機 NLF 處理 A/B。先將本機測試影片複製到 `android/app/src/androidTest/assets/pose3d/A.mp4` 與 `B.mp4`；個人影片不納入 Git。
- `Pose3dPerformanceTest`、`Pose3dPerformanceDeviceTest`：配置規則，以及實機並行／串行時間、程序 PSS、姿勢差異。
- `test/infrastructure/pose_3d_job_test.dart`：並行順序、資源不足回退、返回不中斷、手動取消、設定後重跑、保留舊結果與磁碟快取。
- `test/device/pose_3d_smoke.dart`：Flutter → native → 內插／視角繪製 → MP4 匯出與播放。測完恢復 `lib/main.dart` APK。

推論 FPS 代表每秒「輸出時間軸」的採樣數，不代表手機可達到同樣的即時運算速度。iOS 尚未接上本機推論後端。

## 2026-10-01 並行與介面驗證

SM-S9180（8 核、OS 可用總 RAM 10.77 GiB，開始時可用約 4.13 GiB）。A/B 各取 4 個影格，共 8 次完整採樣；包含載入、解碼、人體框、5 次增強與釋放。每組執行兩次，第二輪反向測試，過程溫度狀態由 0 升至 1：

| 配置 | 第一輪 | 第二輪 | 平均 | 程序峰值 PSS |
|---|---:|---:|---:|---:|
| 依序，4 threads | 24.93 s | 35.77 s | 30.35 s | 480–497 MiB |
| A/B 並行，各 2 threads（採用） | 18.39 s | 21.88 s | 20.14 s | 721 MiB |
| A/B 並行，各 3 threads | 21.52 s | 22.56 s | 22.04 s | 697–708 MiB |

有限採樣下平均耗時降低約 34%；這不是固定溫度的長片基準。所有配置均偵測 8/8，17 關節座標及信心值與串行基準差異為 0。最初使用 STREAM_MODE 時並行有差異，改成逐張框偵測後上述六組通過一致性驗證。不能據此宣稱完整 airflare 影片的姿勢估計精度。

Flutter 27 項測試、JVM 5 項測試及實機並行比對通過，修改範圍的 Dart 分析無問題。基準原始資料位於本機 `build/pose3d-performance.json`。

新版 Flutter → native 並行推論 → 視角繪製 → MP4 → 手機播放器完整流程通過：不同 A/B 裁切與倍速，共同長度 1.2 秒、各 5 次採樣，A 偵測 4/5、B 偵測 5/5；輸出固定並排 720×720、30 FPS、1.2 秒 MP4（57,266 bytes）。失敗影格維持空白。該次測試途中手機鎖屏，整段推論等待 143.8 秒，不作速度基準；速度比較以上方原生實機測試為準。報告與影片在本機 `build/pose3d-parallel-smoke.json`、`build/pose3d-parallel-smoke.mp4`。

## 先前版本驗證（含已移除的 Heavy）

- Flutter 25 項測試通過；NLF 原模型數值比對 3 項 JVM 測試通過。
- SM-S9180 實機：兩項模型測試通過。A/B 各取 3 個時間點，Heavy 偵測 6/6，含解碼單次約 195–324 ms；NLF 偵測 5/6，成功採樣約 2.33–2.75 s（5 次增強融合）。NLF 在 B 的 3 秒處未取得可靠的 2D 人框，因此留空；這是有限採樣的功能測試，非完整影片精度評估。
- Flutter → native 推論 → 內插／視角繪製 → FFmpeg MP4 完整流程通過：不同 A/B 裁切與倍速，共同長度 1.2 秒、各 5 次成功採樣，輸出 720×720、30 FPS、36 影格，手機 video_player 與桌面解碼均成功。
